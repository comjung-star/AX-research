# 연구 전체 진행도 — 쉬운 설명

## 한 줄 요약

이 연구는 쉽게 말하면 다음 순서로 진행된다.

```text
무엇을 연구할지 정한다
→ AX 사례를 모아 도서관을 만든다
→ 검색시험 문제와 정답지를 만든다
→ 기존 검색방법의 점수를 잰다
→ 우리가 만든 다중관점 모델을 구현한다
→ 정말 더 좋은지 비교한다
```

---

## 1. 연구계획서

### 쉬운 말

**"무엇을 연구할지 약속하는 설계도"**

연구계획서에서는 다음을 정한다.

- 어떤 문제를 해결할 것인가?
- 어떤 모델을 만들 것인가?
- 무엇과 비교할 것인가?
- 잘 됐는지 어떻게 측정할 것인가?

### 우리 연구에서는?

기업 사용자가 하나의 업무문제를 입력하면, 그 문제를 여러 관점으로 나눠 관련 AX 사례를 검색하고 AX 전략을 추천하는 모델을 연구한다.

예:

```text
"상담업무가 너무 힘들다"
```

이 한 문장 안에도 여러 문제가 있을 수 있다.

- 문의량이 너무 많다.
- 반복 질문이 많다.
- 필요한 지식을 찾기 어렵다.

우리 연구의 핵심은 이런 관점을 따로 보존하면서 검색하는 것이다.

### 현재 상태

**완료**

---

## 2. Dataset 구축

### 쉬운 말

**"AI가 찾아볼 AX 사례 도서관 만들기"**

검색 모델에게 아무 자료도 주지 않고 사례를 찾으라고 할 수는 없다.

그래서 실제 기업 AX 사례를 동일한 형식으로 정리했다.

### 주요 정보

| 연구용 이름 | 쉬운 뜻 |
|---|---|
| Business Problem | 회사가 무엇 때문에 힘들었나? |
| AX Target / Task | 어떤 업무를 바꾸려고 했나? |
| Business Context | 어떤 환경·조건에서 생긴 문제인가? |
| Strategy | 실제로 어떤 AX 방법을 사용했나? |
| Outcome | 적용 결과가 어땠나? |

### 현재 상태

- Main Dataset v1: **100건**
- Case ID: **AX0001 ~ AX0100**
- QA: PASS
- 상태: **Freeze**

### Freeze란?

실험 중에 정답이나 데이터를 계속 바꾸면 공정한 비교가 안 된다.

그래서 지금의 100건을 **"이번 실험에서는 이 버전을 그대로 사용한다"**고 고정한 것이다.

---

## 3. Retrieval Ground Truth

### 쉬운 말

**"검색시험의 문제지와 정답지 만들기"**

지금 우리가 진행 중인 단계다.

검색 프로그램을 만들기 전에 먼저

> "이 질문에는 어떤 AX 사례가 정답인가?"

를 정해놔야 한다.

정답이 없으면 BM25나 Dense Retrieval이 검색한 결과가 잘한 것인지 판단할 수 없다.

### 구조

```text
업무문제 Query
      ↓
Gold Perspective
      ↓
Perspective × AX Case 관련도 0~4
      ↓
Gold Relevant Cases
      ↓
Gold Strategy Set
```

### Query

사용자가 입력할 업무문제, 즉 **시험문제**다.

예:

> 고객 문의가 너무 많고 반복 질문 처리 때문에 상담직원이 복잡한 업무에 집중하지 못한다.

### Perspective

하나의 문제를 바라보는 **각각의 관점**이다.

예:

- P1: 대량 문의 처리 병목
- P2: 반복 응대 업무 부담
- P3: 지원 지식 접근 및 답변 일관성

### Perspective × Case 관련도

각 관점과 100개 AX 사례가 얼마나 관련 있는지 평가한다.

| 점수 | 의미 |
|---:|---|
| 4 | 직접적으로 매우 관련 |
| 3 | 강하게 관련 |
| 2 | 일부 관련 |
| 1 | 약하게 관련 |
| 0 | 관련 없음 |

현재 Pilot에서는 **3점 이상을 Gold Relevant 후보**로 보는 규칙을 시험하고 있다.

### Gold란?

논문에서 Gold는 **실험 전에 정해놓은 정답**이라는 뜻이다.

모델이 먼저 검색한 결과를 보고 정답을 정하면 안 된다.

### 현재 상태

- Ground Truth Protocol v0.1: 완료
- 평가 Query: 10건 Draft
- Query별 Perspective: 3개씩 Draft
- 실제 Perspective × Case 0~4 라벨링: **다음 작업**

## 4. Baseline 실험

### 쉬운 말

**"기존 방법들의 기본 점수 재기"**

우리 모델이 좋다고 주장하려면 기존 방법보다 실제로 좋아야 한다.

그래서 먼저 기본 검색방법의 점수를 측정한다.

### BM25

**같은 단어가 얼마나 잘 겹치는지를 중요하게 보는 검색**

예:

질문에 "고객 문의", 사례에도 "고객 문의"가 자주 등장하면 높은 점수를 받을 가능성이 크다.

### Dense Retrieval

**문장의 단어가 달라도 뜻이 비슷한지를 숫자 벡터로 비교하는 검색**

예:

- "문의 처리량이 너무 많다"
- "상담 요청 증가로 대응이 지연된다"

단어는 다르지만 의미는 비슷하다고 판단할 수 있다.

### GPT-only

별도의 검색모델 구조 없이 GPT 계열 LLM에게 직접 사례 판단 또는 전략 추천을 시키는 비교 방식이다.

### 비교할 Baseline

1. Single-query BM25
2. Single-query Dense Retrieval
3. GPT-only

### 왜 필요한가?

이 점수들이 우리 모델의 **비교 기준점**이 된다.

## 5. Multi-Perspective 제안모델

### 쉬운 말

**"한 질문을 여러 방향으로 생각해서 각각 검색하기"**

기존 방식:

```text
업무문제 하나
→ 검색 한 번
→ 결과
```

우리 방식:

```text
업무문제 하나
→ P1 관점
→ P2 관점
→ P3 관점
→ 각 관점별 검색
→ 관점별 결과 유지
```

핵심은 여러 관점의 결과를 너무 일찍 하나로 합치지 않는 것이다.

교수 피드백의 중요한 지점도 여기에 있다.

BM25든 Dense Retrieval이든 **단일질의 하나만 사용하면 일부 관점을 초기 검색 단계에서 놓칠 수 있다.**

그리고 초기에 빠진 사례는 나중의 Reranking만으로 다시 살리기 어렵다.

---

## 6. Multi-view / Hybrid Retrieval / Query-Case Interaction

제안모델을 더 정교하게 만드는 단계들이다.

### Multi-view

한 AX 사례를 하나의 문장으로만 보지 않고 나눈다.

- Problem View
- Task View
- Context View

**쉬운 말:** 사례를 한 방향이 아니라 세 가지 정보로 따로 읽는다.

### Hybrid Retrieval

여러 검색방법으로 후보를 넓게 찾는다.

예:

- Dense Retrieval
- Sparse Retrieval(BM25/SPLADE)
- 필요 시 Graph Retrieval

**쉬운 말:** 한 종류의 검색기만 믿지 않고 여러 검색기의 장점을 함께 이용한다.

### Query-Case Interaction

Query와 후보 사례를 더 자세하게 비교해서 점수를 다시 계산한다.

교수 제안 형태:

```text
[q, c, q⊙c, |q-c|]
→ MLP
→ Relevance Score
```

**쉬운 말:** 1차 검색으로 뽑힌 후보를 "이 질문과 정말 잘 맞는가?" 하고 다시 정밀 심사하는 단계다.

---

## 7. Factor Anchor / Wald Evidence

검색 이후 전략 추천을 더 근거 있게 만드는 단계다.

### Root Cause Factor

**문제가 왜 생기는지 공통 원인을 분류한 것**

현재 9개 Factor를 사용한다.

예:

- 반복 수작업
- 정보·지식 분산
- 전문가 판단 의존
- 대량 처리 병목
- 오류·컴플라이언스 위험

### Factor Anchor

검색된 사례를 공통 Root Cause Factor에 연결한다.

**쉬운 말:** 서로 다른 회사 사례라도 "결국 비슷한 원인 때문에 생긴 문제인가?"를 공통 기준점으로 묶는다.

### Wald Evidence

Root Cause와 Strategy가 데이터에서 얼마나 관련되어 나타나는지를 통계적으로 본다.

**주의:** 인과관계를 증명하는 것이 아니라 **연관성 Evidence**다.

---

## 8. 최종 Strategy Recommendation

검색한 사례와 Root Cause, 통계적 근거를 이용해 AX Strategy를 추천한다.

최종적으로 원하는 출력:

- Recommended Strategies
- Traceable Evidence Path
- Actionable Explanation
- Confidence / Priority

### 쉬운 말

단순히

> "RAG 쓰세요"

라고 끝나는 것이 아니라

> "당신의 문제는 지식분산 관점에서 볼 수 있고, 이와 관련된 AX 사례는 AX0010·AX0059이며, 해당 사례에서 이런 전략이 활용됐다."

처럼 **왜 추천했는지 거꾸로 추적할 수 있게 만드는 것**이다.

---

## 9. 최종 평가와 Ablation

### 쉬운 말

**"우리 모델이 정말 좋아졌는지, 그리고 무엇 때문에 좋아졌는지 확인하기"**

### Ablation

기능을 하나씩 빼면서 성능을 비교하는 실험이다.

예:

```text
전체 모델 Recall = 0.80
Multi-Perspective 제거 = 0.65
```

이런 결과가 나오면 Multi-Perspective가 실제 성능 개선에 도움을 줬다고 설명할 근거가 생긴다.
