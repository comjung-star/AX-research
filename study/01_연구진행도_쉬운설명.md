# 연구 전체 진행도 — 쉬운 설명

## 한 줄 요약

이 연구는 쉽게 말하면 다음 순서로 진행된다.

~~~text
AX 사례 도서관 만들기
→ 시험문제와 정답지 만들기
→ 기본 검색기 성능 재기
→ 한 문제를 여러 관점으로 검색해보기
→ 사례를 Problem / Task / Context로 나눠보기
→ 여러 검색기와 재정렬 모델을 붙여보기
→ 무엇이 실제로 도움이 됐는지 하나씩 검증하기
→ 검색된 사례를 Root Cause / 통계근거와 연결하기
→ 최종 AX Strategy 추천
~~~

## 1. 데이터와 정답지 — 완료

- AX 사례: AX0001~AX0100, 100건
- Dev Query: GTQ001~GTQ010, 10건
- Query별 Reference Perspective: 3개
- Perspective × Case relevance: 총 3000 labels
- relevance 3 이상 = Gold

쉽게 말하면 **도서관 100권 + 시험문제 10개 + 정답지**가 준비된 상태다.

## 2. Stage 1 — 한 문제를 여러 관점으로 나누면 좋은가? — 완료

### Single Dense

원래 업무문제 Query 하나를 그대로 BGE-M3 임베딩 검색에 넣는 기본 방식.

### Multi-Perspective Dense

업무문제를 GPT-6 Luna가 2~5개 관점으로 나눈 뒤 각 관점을 Dense 검색하는 방식.

결과:
- 새로운 Gold 사례를 실제로 더 찾기는 함
- 하지만 Top-K 자리가 정해져 있어 기존 Gold가 더 많이 밀려남
- 그래서 전체 Recall은 Single Dense보다 높아지지 않음

핵심 교훈:
> **좋은 후보를 더 많이 찾는 것과, 제한된 Top-K 안에 좋은 후보를 잘 남기는 것은 다른 문제다.**

## 3. Stage 2-1 — 사례를 세 View로 나누면 좋은가? — 완료

한 AX 사례를:
- Problem View
- Task View
- Context View

로 따로 임베딩하고 처음에는 1/3씩 똑같이 합쳤다.

결과:
- 순위는 바뀜
- 성능은 거의 비슷함

즉 **나누기만 한다고 자동으로 좋아지지는 않았다.**

## 4. Stage 2-2 — View별 가중치를 다르게 주면 좋은가? — 완료

Query/Perspective마다 Problem / Task / Context 중요도를 다르게 주는 작은 Gate를 학습했다.

평가할 Query의 정답을 학습에 쓰지 않기 위해 LOQO를 사용했다.

결과:
- Problem 약 60%
- Task 약 0.3%
- Context 약 40%
- Task를 거의 버리는 방향으로 학습됨
- Equal Fusion보다 Recall이 낮아짐

따라서 **현재 Gate v1은 미채택**이다.

## 5. Stage 2-3 — Dense + BM25를 같이 쓰면 좋은가? — 완료

Hybrid Retrieval:
~~~text
같은 Perspective
├─ Dense 검색
└─ BM25 검색
      ↓
Candidate Union
~~~

결과:
- BM25가 Dense와 다른 후보를 실제로 가져옴
- 새로운 Gold도 추가함
- 하지만 검색 슬롯을 50:50으로 나누면 Dense의 깊은 좋은 후보를 잃는 손해가 더 컸음

즉 **보완성은 확인했지만 현재 50:50 방식이 더 좋은 것은 아니었다.**

## 6. Stage 2-4 — 후보를 MLP로 다시 정렬하면 좋은가? — 완료

교수 제안 구조:
~~~text
[q, c, q⊙c, |q-c|]
→ MLP
→ Relevance Score
~~~

같은 후보집합에서 단순하지만 안정적인 RRF와 비교했다.

결과:
- QCI MLP v1이 대부분의 K에서 RRF보다 낮음
- 현재 데이터는 10개 Dev Query라 학습형 모델이 일반화하기에 작을 가능성이 있음

따라서 **QCI MLP v1도 미채택**이다.
다만 Query-Case Interaction 아이디어 자체를 없애는 것은 아니다.

## 7. Ablation은 무슨 의미인가?

우리 연구에서 ablation은 **경우의 수를 지운다는 뜻이 아니라, 구성요소가 실제로 도움이 되는지 따로 떼어 검증하는 것**이다.

예:
~~~text
Multi-view를 넣어봄 → 거의 동일
Gate를 넣어봄       → 악화
Hybrid를 넣어봄     → 보완성은 있음
QCI를 넣어봄        → RRF보다 낮음
~~~

이 결과도 모두 연구 결과다. 성능이 안 좋아졌다고 실험을 삭제하지 않는다.

## 8. 현재 위치 — Stage 3 준비

~~~text
Dataset / GT                     ✅
Stage 1 Multi-Perspective        ✅
Stage 2 Search Core 검증         ✅
Stage 3 Factor / Wald Evidence   ← 현재 다음
Stage 4 최종 Recommendation
Held-out Test
~~~

## 9. Stage 3에서는 무엇을 하나?

검색된 사례를 그냥 보여주는 데서 끝내지 않고, **왜 이 전략을 추천하는지 근거를 연결하는 단계**다.

~~~text
Retrieved Cases
→ Case Evidence
→ Root Cause Factor
→ Wald Evidence
→ Evidence Fusion
→ Strategy Recommendation
~~~

### Root Cause Factor

예:
- F01 반복 수작업
- F02 정보·지식 분산
- F03 전문가 판단 의존
- F04 비정형 복잡성
- F05 프로세스/시스템 분절
- F06 확장성 병목
- F07 데이터 가시성/통합 부족
- F08 오류/컴플라이언스 위험
- F09 예측/최적화 복잡성

### Wald Evidence

Factor와 Strategy가 데이터에서 얼마나 연관되어 나타나는지 통계적으로 보는 보조 근거다.

**인과관계를 증명하는 것이 아니다.**

## 지금 한 문장으로

**검색 Search Core의 구성요소는 Stage 2까지 실제로 모두 분리 검증했고, 이제 검색된 사례를 Root Cause Factor와 Wald 통계근거에 연결하는 Stage 3로 넘어갈 차례다.**
