# 사례 근거 기반 관점 목록 — 1~3단계 완료

2026-11-09. **현재112사례를 바탕으로 구체적인 문제 관점 후보17개를 정리하고, 그중4개에 포함·제외 조건과 원문 근거를 붙여 시범 목록을 만들었다.** 관점–사례31개 조합을 내부 검토해18개 연결은 시범 사용 근거가 있고,7개는 보류,6개는 해당 관점에서 제외했다. 연결된 고유 사례는17개다.

이번 결과는 질문별 추천이나 성능 향상 결과가 아니다. 아직 사용자 질문에서 관점을 선택하는 기능은 구현하지 않았다. 원래 LLM동적관점 모형도 변경하지 않았으며, 사용자와 합의한 별도 설계안의 시범 자료다.

각 상세 문서에는 정의, 포함 조건, 제외 조건, 사용자 질문에 적용할 조건, 모르는 부분, 모든 연결의Problem/Task/Context 원문을 담았다. 포함·제외 조건은 앞으로 질문을 선택할 때의 규칙 초안이며, 모든 연결 사례가 모든 질문 조건을 충족한다는 뜻은 아니다.

### P01 — 업무 지식 탐색 지연

요약 근거로 연결한 사례는 문서·정책 검색 지원(AXALL_US_OMB_2025_02663), 금융자문 내부지식 검색(AXV2N_0110), CAD/CAM 지원지식 검색(AXV2P2_0010_01)이다. 문서나 기존 지식을 찾는 기능과 해당 Problem의 탐색 부담이 함께 있다.

반면 같은 금융권이라도 고객상담 대화록 요약(AXV2H_0081_01)은 이번 관점에서 제외했다. 요약 Task만으로 지식검색 기능이 있다고 볼 수 없기 때문이다. 정형 관리데이터 자연어조회(AXV2H_0078_01)는 문서검색과의 경계를 확정하지 않고 보류했다.

### P02 — 비정형 정보 정리 부담

대출문서 데이터 추출, 보험청구서 정보 추출, 무역금융 필드 추출, 상품카탈로그 속성 정리, 보험신청 자료 추출·분류, 의뢰자료 구조화를 연결했다.

예를 들어 보험청구서 사례의 Problem은 ‘다양한 청구서PDF에서 가입자 정보를 수동 복사’하는 부담이고 Task는 ‘견적용 청구서 정보 추출’이다. 그래서 추출 작업은 지원하지만 견적 산정·보험 승인까지 수행한다고 쓰지 않았다.

### P03 — 자료 대조·검증 부담

의뢰항목 완전성 점검, 주문가격 검증, 신원조회 보고서 검증, 운송청구서 감사, 채용지원서·증빙 대조를 연결했다.

‘불완전 지급지시 수정’ 사례(AXV2C_0068_01)는 관련 문제를 다루지만 **확인과 수정은 다른 행위**이므로 보류했다. 사용자가 확인만 원할 때 수정 기능을 적합하다고 단정할 수 없다. 차량 라벨을 카메라로 검사하는 사례는 이번 문서/등록 데이터 관점에서 제외하고, 별도 시각검사 후보P17로 남겼다.

### P04 — 응대용량·시간대 공백

RV고객 문의의 상시 응대·인계, 전자청구SaaS의 대량·야간 문의 응답, 항공 고객서비스 응대, 보험 자격·보장 음성문의 응대를 연결했다.

단, **모든 사례가 야간·모든 채널·자동 거래처리를 지원하는 것은 아니다.** RV사례는 야간 공백을 명시하지만 항공사 요약만으로24시간 지원을 확정하지 않았다. 고객에게 복잡한 금융질문의 답을 제공하는 NatWest사례는 응대용량 초과 근거가 없어 이번 관점에서 제외했다.

## 3. 연결 타당성 검토 결과

### 업종·단어만 보고 넣지 않았는가?

- 금융권 내부지식 검색과 은행 상담요약을 같은 사례군으로 묶지 않았다.
- 고객문의 응대라도 대기·용량 문제와 복잡한 정보 이해 문제를 구분했다.
- ‘문서’라는 공통점만으로 검색·정보추출·내용검증을 합치지 않았다.
- ‘검증’이라는 단어가 같아도 물리 제품의 영상 검사와 문서 대조를 구분했다.

이것은 원문 기반 경계 사례 검토다. 산업명을 가린 독립 평가나 의미 정확도 측정 실험은 아니다.

### 원문에 없는 기능을 추가하지 않았는가?

수행 기능은Task인용을 필수로 뒀다. Problem에 필요한 기능이 적혀 있다는 이유만으로 실제 구현됐다고 하지 않았다. 추출→검증, 확인→수정, 답변→거래처리, 인계→맥락 손실 해결을 자동으로 확대하지 않았다. 채용 합격 결정, 대금 차감, 보험금 지급, 임의 시스템 쓰기 등의 기능은 근거가 없으면 미확인으로 남겼다.

‘지원한다’는 상태는 **저장된 요약이 해당 문제·수행 기능의 연결을 뒷받침한다**는 뜻이다. 원출판물 전체의 사실성이나 새로운 사용자 질문의 정답성을 확정한 것이 아니다.

### 너무 넓거나 중복되지 않았는가?

4개 관점의6개 쌍을 모두 검토했다. 모두 업무시간 부담을 다루지만 검색·추출·검증·응대라는 필요한 작업이 다르므로 시범에서는 분리했다. 이름을 ‘업무 효율화’로 합치면 이 경계가 사라진다.

한 사례의 복수 연결은 허용했다. 의뢰자료 사례AXALL_US_OMB_2025_01754의Task는 다음과 같다.

> Referral data structuring and completeness checks

여기에는 **구조화(P02)**와 **완전성 점검(P03)** 두 작업이 모두 명시돼 있다. 그래서 양쪽에 연결하되, 실제 질문에서 요구한 부분을 다시 골라야 한다. 사례가 겹친다는 이유만으로 두 관점이 같은 것은 아니다.

### 초안에서 실제로 수정한 연결

시스템 통합검색 사례AXV24_f27ca1e6fb82는 초안에서P01지원으로 연결했으나, 검토 후 **보류**로 내렸다. Task는 검색이지만Problem은 ‘여러시스템 연동을 별도 구축하는 부담’이며, 직원이 긴 문서를 찾느라 시간을 쓴다는 근거는 분명하지 않았다. 기능 이름의 유사성과 문제의 일치를 구분한 수정이다. 초안도 [별도 보존](catalog.json)했다.
