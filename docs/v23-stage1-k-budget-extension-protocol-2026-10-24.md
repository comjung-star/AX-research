# AX v2.3 Stage1 K-budget and candidate shortlist extension — diagnostic protocol

작성일: 2026-10-24. **Exploratory protocol**, after having inspected existing Stage1 @10 and @20 aggregate results; **not confirmatory preregistration**. This protocol freezes the two new Top20 merge alternatives *before their specific comparison in this session*. No changes to the already frozen historic experiment, data, or GT.

## Source
Frozen `release/ax-v2.3-stage1-to4-dev-20261023`, BGE-M3 dense branch rankings `experiments/v23_dev/stage1/branch_rankings.csv` (84 ranked cases per generated branch), saved Single/MP ranks `rankings_top20.csv`, Silver qrels 2520, perspective generation 97. 10 repeated Dev queries × three MP runs each; one Single Dense ranking per query. Silver-positive relevance >=3, per-query union of the 3 reference perspectives. All methods are label-blind in candidate scoring.

## Analysis plan
1. **Matched final K sensitivity**: evaluate Single Dense and original MP branch-balanced round-robin at K=5/10/15/20 with identical K within a comparison; macro Recall@K and per-run MP-only vs Single new Silver-relevant, Single-only lost Silver-relevant. K=5/10/20 already present in original Stage1 and will be exact replay consistency checks; K=15 is new interpolation, with no new embeddings.
2. **Top10 Single-positive attrition recovery**: take each q×run Single Dense Top10 Silver-positive that is missing from original MP Top10, and count if recovered by original MP Top15 and/or Top20. Distinguish this **fixed Top10 anchor** analysis from matched-budget K=15/20 comparisons.
3. **Candidate union only, NOT final output**: branch local Top3/5/10/20 unique case unions, report mean unique candidate count and q-level union Silver relevance Recall; these unions exceed output budgets, so do NOT compare their raw Recall to Single Top10/20 as an equal-budget victory. No GT in retrieval or union building.
4. **K20 alternative merge** using existing label-blind C1/C2 algorithms from `docs/v23-stage1-branch-merge-diagnostic-protocol-2026-10-24.md`; ONLY increase final K to 20, keeping fixed local Top20 candidate pool and one selected Top branch case per dynamic branch as quota. C1 fill priority (a) support count among branches local Top10 descending, (b) minimum branch rank ascending, (c) mean of local ranks <=20 ascending, (d) lexical case ID; C2 fill priority maximum branch-wise z-score (scores normalized across all 84 candidates per branch) descending, then C1 support and best rank, case ID. No original-query anchor C3 in the pure-MP Top20 comparison. For B0 use exact stored MP Top20. Do not tune any parameters or scoring from held-out qrels.
5. Evaluate equal Top20 candidates on Recall@20, MP-only Silver relevant, lost Single relevant, perspective coverage, and repeat-level origin. For fair analyses candidate pool and final Top20 both size-aware; C1/C2 use branch Top20 candidate unions and emit exactly 20 unique IDs. No human Gold or independent test.

## Discussion guardrails
- The project architecture can take more candidate cases to the Stage2/3 evidence and scoring components, but the **currently recorded Stage3/4 scripts explicitly use Top10**, and cannot be claimed validated at Top20 without a new follow-up run and separate output/evidence quality test.
- We have checked baseline Top20 figures **before writing this protocol**. The protocol is NOT evidence of independent or prospective external validation. The v2.3 corpus was selected with Dev context; don't infer superiority/generalization from it.
- Top20 increasing absolute Recall is expected for all comparable ranking systems, so improvement **relative to Single at same K**, MP-only novel relevant discovery, relevance density, and downstream output quality must be distinguished.
