# 독립 검증 AI 실험 결과 — 반복된 근거 위반으로 중단

기준 커밋 `3e0e7517d09c49af1cd375639cfb9ea5549db3a4`에서 새 브랜치 `research/stage123-independent-verifier-20261027`를 만들었다. 기존 112개 사례, 과거872점과 모든 실험 결과를 보존했다. Stage4 독립Test는 열거나 실행하지 않았다.

## 1. 무엇을 바꿨나

평가 AI와 다른 회사의 검증 AI가 같은 원문을 따로 읽게 했다. 검증 AI에는 앞선 답·점수·추출 목록·예상 점수를 제공하지 않았다.

|평가 모델|별도 검증 모델|
|---|---|
|GPT `gpt-6-luna`|Gemini `gemini-3.5-flash-lite`|
|Gemini `gemini-3.5-flash-lite`|Claude `claude-haiku-4-5-20251001`|
|Claude `claude-haiku-4-5-20251001`|GPT `gpt-6-luna`|

첫 추출은 이전에 질문과 Problem을 숨기고 Task·Context만 읽어 만든 18사례/모델 수행 목록을 출처·해시와 함께 재사용했다. 평가 모델은 자기 목록을 조언으로만 사용하고 원문과 다시 대조한다. 검증 모델은 이 목록도 보지 않는다. 새 모델로 바꾸거나 같은 모델을3종처럼 세지 않았다.

숫자 위치 대신 명시적인 업무 요구ID를 사용했다. 전체 문제와 특정 관점을 구분했다. 실제 수행 근거는 Task·Context에서만, 추가 문제 조건은 Problem·Context에서만 인용하게 했다. 두 판단이 다르면 점수는 보류하며0점으로 바꾸지 않는다. 두 AI가 같게 판단해도 사람이 검증한 정답으로 승인하지 않는다. 검증 때문에 검색 후보를 삭제하지 않았다. 검색 자체는 아직 실행하지 않았다.

## 2. 작은 기준표와 실제 결과

`review_table.md`와 `plan.json`에 20쌍을 고정했다. 직접·부분·무관·겉보기 혼동 각5쌍이며 네 개발 질문을 사용했다. 기존 실패 조합과 다른 업종의 질문응답 사례를 포함했다. 모든 행은 **AI가 만든 검토용 기준표이며 사람 검토가 필요하다**. 예상 점수는 모델 입력에 넣지 않았다. 일부 예상 범위도 검토 대상이다.

20쌍×3평가 모델×평가·검증2단계로 **120개 모델 응답 행, 60개 평가·검증 조합**을 확보했다. 이는 120개의 독립 질문·사례가 아니다. 형식만 수정한 버전에서 이미 유효하게 받은 응답을 출처와 함께 재사용했으며 같은 응답을 새 호출 비용으로 중복 계산하지 않았다.

- 원인 분석을 데이터 통합으로 직접 연결한 Gemini 검증 응답이 있었다. GPT평가는 연결을 제시하지 않아 프로그램이 보류했다. **검증 모델 자체도 틀릴 수 있다는 실제 사례**다.
- 다른 두 평가·검증 조합은 해당 원인 분석 사례를 데이터 통합의 보조 작업2점으로 판단했다. 하지만 양측 설명에 ‘분석하려면 통합이 필요하다’는 원문으로 입증되지 않은 추정이 남았다. 2점의 타당성도 검토 대상으로 남겼다.
- 계약서 요약은 요구 설명에서 부분 관련 가능성을 인정했는데 두 모델이 모두 연결 없음으로 판단한 조합이 있었다. 과도한 제외 가능성을 표시했다. 다수결로 승인하지 않았다.
- 4점 후보에는 같은 원문 조건을 두 모델이 인용한 경우가 있었다. 다만 ‘주의가 분산된다/수작업 부담’ 같은 넓은 설명만으로 추가 점수를 주어도 되는지는 별도 검토가 필요하다. 회의 요약·다음 단계라는 실제 두 업무가4점을 정당화할 가능성과 잘못된 추가점수 경로를 구분했다.

원문·판단·후보 점수·보류 사유는 `semantic_audit.json`에 있다. 사람Gold가 없으므로 기존 방식보다 정확도가 몇% 높아졌다고 주장하지 않는다. 기준표에 맞춰 의미 규칙을 바꾸거나 이를 독립Test 성능으로 발표하지 않았다.

## 3. 왜 멈췄나

같은4사례를1·2·4개씩 묶는 반복 시험을 시작했다. 첫1개 배치에서 Claude의 독립 검증이 다음처럼 답했다.

- 잘못 주장한 수행: `Integrate MES, ERP and quality systems data`
- 실제 원문에 없는 산출물: 통합 운영 데이터

첫 응답은 원인 분석 문장을 인용하면서 수행 행동을 데이터 통합으로 바꿨다. 형식 재시험에서도 `Consolidate fragmented MES, ERP and quality systems data`를 주장했고, 이번에는 Problem 문장을 수행 근거로 인용했다. 두 응답 모두 검사에 실패했다. 첫 응답의 구조 오류를 고쳐도 **실제 기능의 의미 오류가 남는다는 점**이 중요하다.

정확한 위치는 `json-normalization-v6/attempts/claude/stability_0000_gemini_review_a1.json`과 `..._a2.json`이다. `gate.json`에도 원문과 응답을 함께 보존했다. 정상적인 점수 차이가 아닌 반복된 수행 기능 추측이므로 사용자 지정 중단 조건을 적용했다.

반복 시험에서 구조 검사를 통과한 모델 응답 행은3개이고, 평가·검증 쌍이 모두 준비된 결과는0개다. 따라서 **배치1·2·4 비교는 미완료이며 가장 안정적인 배치를 선택하지 않았다**. 이전2→4→4점 현상이 해결됐다고 주장할 수 없다. 이3개는20쌍 기준표120행과 별도다.

## 4. 형식·호출 오류는 어떻게 처리했나

Claude의 복잡한 JSON Schema를 다시 사용하지 않았다. 단순 JSON과 로컬 검사만 사용했다. 이번에 복잡도 HTTP400은 없었다.

일반적인 형식 문제는 여러 버전으로 고쳤고 이전 응답을 덮어쓰지 않았다.

1. 사례 ID를 요구 ID로 잘못 쓰는 응답, 빈 사례 배열, 긴 이유를 거부했다. 이유 길이는 의미 점수와 무관한 형식 조건으로16→32단어로 바꾸고 프롬프트·검사 조건을 일치시켰다. 원문을 잘라 맞추지 않았다.
2. 빈 연결도 사례를 반드시 포함하는 예를 추가했고 출력 한도를 늘려 잘림을 줄였다.
3. 한 사례 요청은 응답에 AI가 다시 사례ID를 쓰게 하지 않고, 요청에 담긴 유일한 사례와 요청 해시로 연결했다. 여러 사례는 정확한 사례 키 집합을 검사한다. 다른 질문 ID·중복 JSON 키·잘못된 원문 인용은 거부한다.
4. 완결된 JSON 코드블록만 분리해 읽을 수 있게 했다. 블록 밖 설명은 삭제하지 않고 원응답에 보존하며 추가 감사 대상으로 표시했다. 누락 ID·근거·점수를 만들어 넣지 않았다.
5. Gemini HTTP4291건은 원래 비용 예약을 유지하고 충분한 간격 뒤 한 차례만 복구했다. 이후 호출 간격을 늘렸다. 타임아웃처럼 수신 여부가 불분명한 요청을 자동 재전송하는 경로는 허용하지 않았다. [Google 공식 지침](https://ai.google.dev/gemini-api/docs/troubleshooting)에 따라 횟수를 제한했다. 제한 종류가 분당인지 일별인지까지 확인한 것은 아니다.

이 변경은 형식·전송 복구다. 그것만으로 기능 판단이 더 정확해졌다는 뜻은 아니다. 원래 검증에서 거부된 응답도 전부 보존했고 원요청 버전과 재검증 버전을 구분했다.

## 7. 교수님께 설명할 결과와 다음 단계

이번에 보여준 것은 검색 성능 개선이 아니라 **평가 방식의 한계와 방어 장치의 실제 동작**이다. 독립 검토는 틀린 직접 연결을 보류시키는 데 도움이 됐지만, 검증 AI도 같은 수행 기능을 추측했다. AI 둘이 같은 말을 한다는 이유로 정답이 되지는 않았다. 다른 업종의 질문응답을 관련 사례로 유지했다는 작은 개발 관찰도 남겼다.

추가 개선은 먼저 실패한 검증 단계에 한정해야 한다. 원문에서 실제 수행·필요 조건·추가 성과를 구별하는 검토를 강화하고, ‘원인 분석만 있음/실제 통합도 있음’을 구분한 미사용 개발 사례로 확인해야 한다. 사람이 가능하면 이 작은 기능 연결부터 확인하는 것이 도움이 된다. 사람 검토가 없으면 계속 AI Silver로만 표현해야 한다. 표본을 보고 규칙을 바꾼 뒤 같은 표본의 성능을 독립 검증 성능이라고 부르면 안 된다.

4점의 추가 상황 근거도 별도 검증이 필요하다. 두 인용이 마침표 하나 때문에 달라져3·4점이 갈리는 현상은 의미가 아니라 표현의 문제다. 추가업무 두 개가 같은 원문 한 문장에 있다는 이유로 점수가 낮아질 수도 있다. 이번 실패 표본에 맞춰 최종 규칙을 사후 수정하지 않고, 후속 미사용 표본 검증이 필요한 한계로 기록했다.

평가자·검증자 순환 배정의 영향, 선택된 개발 표본20개, 공통 프롬프트의 편향, 과거 응답 재사용과 형식 버전 차이도 한계다. 112사례의 원인터넷 출처를 이번에 새로 전부 검증한 것은 아니다. 교수님 피드백의 근거성·독립 평가·공정 실험 원칙은 절차에 반영했지만, 신뢰할 전수 정답과 검색 효과 입증은 아직 충족하지 못했다.

교수님이 직접 제기한 Dev/Test·정답 구축과 동적 관점의 관계에 관한 우려와, 이번 독립 검증 AI라는 실험 선택은 구분한다. 독립 검증 AI의 구체적 배정을 교수님이 제안·승인한 설계로 표현하지 않는다.

## 재현 자료

`input_preservation.json`은 입력3개 파일이 기준 커밋과 바이트 단위로 같은지 검사한다. `test_results.json`의 새로운 자동 검사13개는 통과했다. 이는 코드·안전 조건 검사이며 AI 정확도를 증명하지 않는다.

API 호출 없이 `PYTHONPATH=src;.`에서 `python -m scripts.independent_verifier_closeout`으로 집계·근거 감사·비용 기록을 재생성할 수 있다. `python -m pytest tests/test_independent_verifier.py tests/test_independent_verifier_binding.py -q`로 검사한다. 활성 `halt.json`과 실패 `gate.json`을 유지한다. 중단 파일을 지워 재개하면 안 된다. 요청·응답·응답 모델ID·입력 버전·사용량·예약·실패는 각 버전의 `attempts`, `results`, `counts`에 보존했다.
