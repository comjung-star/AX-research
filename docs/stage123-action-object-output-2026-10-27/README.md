## 바꾼 평가 기준

이전에는 인력 여유·업무 부담 감소라는 효과가 실제 수행 과업과 혼동됐고, 업종·수신자 차이도 일관되게 다루지 못했다. 새 기준은 **행동–기능적 대상–산출물**을 비교한다. 같은 기능을 수행하면 다른 업종의 사례도 유용한 관련 사례다. 예를 들어 쇼핑·직원·배달원·법률 질문도 실제 질문에 답한다면 ‘문의 답변’에 직접 관련될 수 있다. 단순 수작업 감소만으로 관련성을 만들지는 않는다.

|점수|새 기준|
|---|---|
|0|작업 연결이 없음. 수작업·시간 절감이나 업종만 같은 것은 근거가 아님|
|1|넓은 작업군·대상은 비슷하지만 실제 행동/산출물과 명시적 지원 단계가 다름|
|2|지원·상하류 단계이거나 행동/대상/산출물 중 일부만 일치|
|3|핵심 행동과 기능적으로 같은 대상·산출물이 명시됨. 효과를 추측하지 않아도 직접 관련|
|4|3점에 더해 대상의 주요 작업과 문제 조건 대부분이 원문으로 뒷받침됨|

전체 질문은 핵심 작업 중 하나에 직접 맞으면3점이다. 복합 질문의4점은 두 작업이면 둘, 세 작업이면 최소둘과 문제 조건을 충족해야 한다. 개별 관점은 지정한 작업만 평가하므로, 제조 일정조정이 전체 제조 질문에 관련돼도 ‘품질 원인분석’ 관점에 그 점수를 가져올 수 없다.

요약·추출·검증·후속조치 식별은 다른 작업이고, 결함 존재 탐지와 원인 진단도 다르다. 특히 사례 **Problem에 어떤 결과가 필요하다고 적힌 것**은 **Task가 실제 그 작업을 한다는 증거가 아니다.** 보안·기술·성과·인력 여유를 원문 밖에서 채우지 않도록 명시했다.

원래 질문10개/참조관점30개는 변경하지 않았다. 새 관점 검증은 원질문 인용에 근거한 별도4개 작업 관점이다. 런타임의 고정 범주가 아니며, 향후 동적 관점 생성에는 원질문만 넣도록 별도 입력을 준비했다. [정책 원문](protocol.md), [질문별 작업 정의](../../configs/aoo_task_rubric_20261027.json), [v10 보완 내역](schema-safe-v10/protocol-delta.md).

## 실제 재시험과 남은 문제

중단에는 다음의 구체적 근거가 있다. 단순한 등급 차이만을 오류라고 부른 것이 아니다.

1. **Gemini의 전체 질문4점 근거 부족.** 쇼핑 질문 답변 사례 `AXV2P2_0048_01`은 기능상 QA이므로 다른 업종이라도3점이 가능하다. 그러나 Gemini는 여전히4점과 `problem_context=SUPPORTED`를 줬다. 사례 원문에는 문의 과부하·상담 인력 제약·답변 일관성 조건이 없다. 코드가 받는 ‘조건 충족’ 표기만으로 실제 근거를 보장할 수 없었다. 단일 QA 관점의4점과 달리 전체 질문의 추가 조건이 문제다.
2. **Problem의 필요와 Task의 수행을 혼동한 흔적.** 이메일 요약 사례 `AXV2H_0002_01`의 Task는 ‘고객 이메일 요약’이다. Claude는 실제 수행 작업 목록에 `IDENTIFY_FOLLOWUP`도 포함했다. 후속조치 확인의 부담은 Problem에 있지만, Task가 후속조치를 식별한다는 명시는 없다. 전체 질문에서 요약 하나로3점은 가능하더라도, 이를 개별 후속조치 관점의 검증으로 사용할 수는 없다.
3. **지시를 넘는 이유 서술.** Claude의 다른6사례 응답은 길이와 이유 조건을 통과하지 못했다. 실제 QA 행동은 포착했지만, 이유에 인력 여유·규모·반복 질문 처리시간 감소를 덧붙였다. 예측 효과를 지우거나 원점수를 임의로 낮춰 통과시키지 않았다.
4. **최대 출력 구조의 생성 호환성 미확인.** Claude는8사례·3과업 구조에 HTTP400을 반환했다. 앞선16출력토큰 상한 진단에서 받은 메시지는 `Schema is too complex.`다. 인증 실패와 구분되며, 작은 요청 하나는 성공했지만 최대 구조는 여전히 실패했다. 토큰 계산 성공은 실제 생성 문법의 호환성을 증명하지 않는다.

검토한 응답에서 다른 질문/사례 ID로 바꿔 평가한 증거는 확인하지 않았지만, 모든108개 이유를 검증했다고 주장하지 않는다. 일부 직접 사례의2/3 차이와 부분/무관 점수 차이는 그대로 남긴다. 상식적 진단 기대구간을 사람 정답처럼 사용해 ‘정확도’를 꾸미지도 않는다.

## 해결책과 재개 순서

1. ‘직접 작업3점’과 ‘원문으로 확인한 추가 문제 조건4점’을 분리하고, 각 조건의 원문 근거를 대조한다. 전체 점수를 모델이 직관적으로 다시 매기기보다 핵심 작업별 일치 근거를 받은 뒤 사전 고정 규칙으로 합산하는 방안을 작은 표본에서 검증한다. 원래 모델 점수는 덮어쓰지 않는다.
2. 실제 수행 능력은 Task/운영상 Context로, 원하는 결과·어려움은 Problem으로 구분한다. 후속조치 식별/요약·탐지/원인분석의 경계와 다른 업종의 동등 작업을 사람/전문가가 확인할 수 있으면 확인한다. 없으면 계속 AI Silver 한계를 명시한다.
3. API 출력구조를 더 줄이거나 배치를 작게 하고, 최대 실제 생성 모양을 먼저 확인한다. 토큰 계산만으로 호환성을 승인하지 않는다. 바뀐 입력은 다시 비용을 측정하고 과거 실패 비용 예약도 유지한다.
4. 전체 균형36쌍의3종 독립 평가와 전체/관점 대조가 모두 통과해야 새3,360점→Stage2→Stage3 순으로 진행한다. 독립 Test는 계속 봉인한다.
