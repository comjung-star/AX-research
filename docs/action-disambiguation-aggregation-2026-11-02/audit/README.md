# 오탐/업무 차이 원인 분석(평가 전)

확인한 것은 기존 구조화 Task와 프로필이다. 원 출판물 재검증이나 사람Gold가 아니다. 검토를 검증으로 합친 구현은 직접 추적했고, 다른 업무 유형은 별개 기능이라는 근거만으로 무관 정답을 만들지 않는다.

|유형|관찰 근거|판정 범위|
|---|---|---|
|읽기·요약 / 검증|Q2 핵심·후속조치 파악 관점의 검토가 보고서 검증/청구서 감사와 validate_record를 공유|실제 규칙의 기능 혼동. 원문에는 검증 요구가 없음|
|조회·검색 / 분석|검색 기능 원질문과 원인분석/예측 Task를 전수 대조|다른 기능일 뿐 관련성은 별도 검토 필요|
|분류 / 평가·승인|태깅 원질문과 심사·검증 Task 비교|검증을 승인 실행이라고 추정하지 않음|
|안내·답변 / 실행|질문 응답과 예약/환불/회계처리 같은 명시 Task 비교|안내가 실제 시스템 실행을 했다는 근거 아님|
|예측 / 탐지·모니터링|forecast_quantity와detect_anomaly 비교|예방정비를 돕더라도 현재 감지와 미래 예측을 동일 기능으로 취급하지 않음|

## 대표 오류의 점수 기여

|사례|실제Task|원문규칙|관점최고규칙|원문의미|관점최고의미|C점수|C순위|
|---|---|---:|---:|---:|---:|---:|---:|
|AXV2H_0003_01|직원 신원조회 보고서 검증|1|4|0.482663|0.504717|0.873423|4|
|AXV2P2_0011_01|Audit freight invoices for overcharges|1|4|0.427463|0.434381|0.857731|6|

원문을 관점에 덧붙이지 않는다. 원문 기능/관점 기능/사례 실제Task를 별도로 비교한다. 원질문은 읽기·요약·후속조치이며 관점 제목의 ‘검토’가 규칙 고득점을 만들었다. B는 기능 확률이 아닌 필드 cosine이다. C의 높은 규칙 성분0.5가 최종점수를 크게 올렸고 최고관점 규칙이 원문 저점수를 덮었다.

전수 기록은 type_analysis.json, 최고관점 승격은 branch_promotions.json, 원문/Task/각관점/점수 상세는 mandatory_examples.json에 있다.

추가로 Create CRM contacts from customer emails는 출력CRM연락처와 입력이메일이 다르지만 기존 generate_content는Create+emails를 같은 기능으로 묶는다. 이는 출력대상과 입력자료 역할을 혼동한 실제 문법 사례다. 이번 C1은 명시 from/using 기반 입력자료를 출력으로 인정하지 않는 보수적 처리를 검토한다.
